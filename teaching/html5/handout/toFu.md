# Internet Handout

## OSI 7 Layer Structure
OSI 模型(Open Systems Interconnection Model)是由國際標準化組織(ISO)所制定的網路通訊概念架構，它將網路通訊的過程分為 7 個不同的層次(Layer)，每一層都有其特定的職責，從底層的硬體訊號一直到最上層的使用者應用程式
以下是 OSI 網路 7 層架構的完整列表(由上至下)：


| 層級(Layer) | 中文名稱 | 英文名稱 | 主要功能與職責 | 常見協定與硬體設備 |
| :--- | :--- | :--- | :--- | :--- |
| L7 | 應用層 | Application | 直接提供使用者網路服務與互動介面 | HTTP, HTTPS, FTP, DNS |
| L6 | 展示層(表現層) | Presentation | 負責資料格式轉換、加密/解密、壓縮/解壓縮 | SSL/TLS, JSON, JPEG |
| L5 | 會議層 | Session | 建立、管理與終止應用程式之間的通訊連線 | NetBIOS, RPC |
| L4 | 傳輸層 | Transport | 負責端對端的可靠資料傳輸、流量控制與封包切割 | TCP, UDP |
| L3 | 網路層 | Network | 負責跨網路的定址(IP 排序)與路徑選擇(路由) | IP, ICMP；路由器(Router) |
| L2 | 資料連結層 | Data Link | 同一區域網路內的可靠傳輸，處理 MAC 位址與錯誤檢測 | Ethernet, Wi-Fi；交換器(Switch) |
| L1 | 實體層 | Physical | 負責實體硬體媒介上的原始 Bits(0 與 1 訊號)傳輸 | 網路線、光纖；集線器(Hub) |
||||||

### Compare to OSI and TCP/IP Structure
TCP/IP 四層架構(Internet protocol structure) 與 OSI 七層模型的對應關係，主要是將 OSI 較為細分的上三層與下兩層進行了整合與簡化，TCP/IP 是目前網際網路實際運作所使用的架構，以下是它們之間的完整對應表格：

| OSI 7 Layer | TCP/IP 4 Layer | Function | PDU |
| :--- | :--- | :--- | :--- |
| Application(L7)<br>Presentation(L6)<br>Session(L5) | 1. Application | 整合了資料格式、加密與使用者介面，直接為應用程式提供網路服務(如網頁瀏覽、郵件) | Data |
| L4(Transport) | 2.(Transport) | 負責端對端的通訊品質、流量控制與錯誤檢查，最核心的是 TCP 與 UDP 協定 | Segment/(TCP)<br>Datagram(UDP) |
| L3(Network) | 3.(Internet) | 負責將封包透過最佳路徑傳送到目的端，主要處理 IP 位址與路由選擇 | Packet(封包) |
| L2(Data Link)<br>L1(Physical) | 4.(Network Interface)<br>(or Link Layer) | 負責處理實體硬體(如網卡、網路線)與區域網路內的資料訊號傳輸 | Frame/ Bits |
|||||
> PDU 是 Protocol Data Unit 的縮寫，中文翻譯成協定數據單元，每一層網路架構所使用的資料單位名稱

#### OSI 與 TCP/IP 架構核心差異

-  實用導向 vs 概念導向： OSI 模型是先有理論才定義規格，定義得非常嚴謹且理想化；而 TCP/IP 是伴隨網際網路實際發展出來的，因此更符合實際工程應用
-  上三層的合併： 在 TCP/IP 中，展示層(加密/壓縮)與會議層(連線管理)的功能通常直接交由應用程式本身或特定的應用層協定(如 HTTPS 的 SSL/TLS)來處理，因此在架構上被併入應用層
- 下兩層的合併： TCP/IP 將底層的物理硬體與區域網路定址視為一個整體，通稱為網路介面層，只要能讓 IP 封包在實體媒介上傳送即可

### 資料封裝(Data Encapsulation)
網路資料的封裝(Encapsulation)與解封裝(De-encapsulation)，就像是寄快遞的過程當你傳送資料(如傳訊息、點網頁)時，資料會從上到下穿過網路層級，每一層都會像包包裹一樣，在資料前端加入該層的控制標頭(Header)
這套機制能讓兩台電腦在相同的層級上，使用相同的網路協定進行對話

📦 資料封裝流程(傳送端⬇️由上至下)

當你從電腦發送資料時，資料會經歷以下五個核心步驟的包裝：

1. 應用程式產生原始資料(Data)
    - OSI L7 應用層 ≫ L5 會議層(或 TCP/IP 應用層)
    - 使用者操作軟體(如瀏覽器輸入網址)，系統產生原始的應用程式資料(Data)

2. L4 傳輸層：加入 L4 標頭 ≫ 變成資料段(Segment)
	- 傳輸層將龐大的資料切成小塊，並在前面貼上 L4 Header
	- 來源連接埠(Source Port)與目的連接埠(Destination Port)，例如網頁是 Port 80 或 443，用來識別是由哪個應用程式發出，該由哪個應用程式接收?
3. L3 網路層：加入 L3 標頭 ≫ 變成封包(Packet)
	- 網路層收到 Segment 後，在外面再包一層 L3 Header
	- 來源 IP 位址與目的 IP 位址這就像在信封寫上寄件人和收件人的地址，讓路由器知道要把封包送到地球上的哪台電腦?
4. L2 資料連結層：加入 L2 標頭與尾標 ≫ 變成訊框(Frame)
	- 資料連結層收到 Packet 後，貼上 L2 Header，並在尾端加入 Trailer(FCS 錯誤檢測碼)
	- 來源 MAC 位址與下一跳的預設閘道/路由器 MAC 位址這用於區域網路(LAN)內相鄰設備間的精準傳送
5. L1 實體層：轉換為訊號傳輸 ≫ 變成 Bits
	- 實體層將 Frame 轉換為由 0 與 1 組成的 Bits，透過網路線、光纖或 Wi-Fi 無線電波，將訊號發射出去

| 層級(Layer) | 封裝動作說明 | 資料單位(PDU) | 加入哪些控制資訊 |
| :--- | :--- | :--- | :--- |
| **L7~L5 應用/展示/會議** | 應用程式啟動，產生初始的原始資料 | **Data** | 應用程式本身的格式(如 HTTP 標頭、JSON 結構) |
| **L4 傳輸層** | 將資料切割成合適大小，並加入 L4 標頭 | **Segment** | **Port(連接埠)**：區分是哪一個應用程式發出的 |
| **L3 網路層** | 在資料段的外層，進一步包裹 L3 標頭 | **Packet** | **來源與目的 IP 位址**：決定跨網路的寄送路徑 |
| **L2 資料連結層** | 在封包前後分別加入 L2 標頭與尾標 | **Frame** | **MAC 位址**(區域網路識別)與 **FCS 錯誤檢測碼** |
| **L1 實體層** | 將訊框轉換成物理媒介可以傳輸的訊號 | **Bits** | 無(直接將 0 與 1 轉換為電壓、光脈衝或無線電波) |
|||||

🔓 資料解封裝流程(接收端⬆️由下至上)

當目標電腦(或伺服器)收到訊號後，會執行完全相反的拆包裹(解封裝)動作
- L1 實體層： 接收物理訊號，將其還原為 Bits，向上傳遞
- L2 資料連結層： 檢查 MAC 位址 是否正確，確認資料無損後，拆掉 L2 Header/Trailer，將裡面的 Packet 往上傳
- L3 網路層： 檢查 IP 位址 是否符合自己，確認無誤後，拆掉 L3 Header，將裡面的 Segment 往上傳
- L4 傳輸層： 根據 Port(連接埠) 號碼，確認這是屬於哪個應用程式的資料，並負責把切碎的資料重組還原，拆掉 L4 Header
- 應用層： 應用程式(如網頁伺服器)拿到最乾淨的原始資料，處理後秀出網頁畫面給使用者

| 層級(Layer) | 封裝說明 | 資料單位(PDU) | 加入哪些控制資訊 |
| :--- | :--- | :--- | :--- |
| **L1 實體層** | 將訊框轉換成物理媒介可以傳輸的訊號 | **Bits** | 無(直接將 0 與 1 轉換為電壓、光脈衝或無線電波) |
| **L2 資料連結層** | 在封包前後分別加入 L2 標頭與尾標 | **Frame** | **MAC 位址**(區域網路識別)與 **FCS 錯誤檢測碼** |
| **L3 網路層** | 在資料段的外層，進一步包裹 L3 標頭 | **Packet** | **來源與目的 IP 位址**：決定跨網路的寄送路徑 |
| **L4 傳輸層** | 將資料切割成合適大小，並加入 L4 標頭 | **Segment** | **Port(連接埠)**：區分是哪一個應用程式發出的 |
| **L7~L5 應用/展示/會議** | 應用程式啟動，產生初始的原始資料 | **Data** | 應用程式本身的格式(如 HTTP 標頭、JSON 結構) |

## IPv4 Classful Addressing
傳統 IPv4 定址分類法(Classful Addressing)是網際網路早期(1981年由 [RFC 791](https://www.rfc-editor.org/info/rfc791/) 定義)所使用的 IP 管理機制在網路規模還很小的那個年代，為了讓路由器能以最快的速度分類與轉發封包，科學家將整個 IPv4 的位址空間(共 232 = 約 43 億個 IP)硬性切割成 A、B、C、D、E 五大類別，其核心設計思想是**用固定的邊界，區分網路大小**

在傳統分類法中，32 位元的 IP 被切割分為兩個部分
1. 網路號(Network address)： 代表設備屬於哪一個**車隊**或**社區**，相同的網路號代表在同一個區域網路內
2. 主機號(Host address)： 代表設備在這個社區裡的**門牌號碼**

它的切割邊界非常死板，完全依照 Byte(即 8 個位元)來對齊
- Class A： 拿 1 個 Byte 當網路號，剩下的 3 個 Bytes 全給主機
- Class B： 拿 2 個 Bytes 當網路號，剩下的 2 個 Bytes 給主機
- Class C： 拿 3 個 Bytes 當網路號，剩下的 1 個 Byte 給主機

![](/images/html5/ipClass.png)

為了讓路由器**一眼看穿**這是哪一類的 IP，傳統定址法利用 IP 第一個字節最左邊的二進位位元(首位元特徵)來做為分類標記

- Class A：巨型網路(政府、跨國企業、電信商)
	- 二進位特徵： 必須以 0 開頭(格式為 0xxxxxxx)
	- 十進位範圍： 1.0.0.0 ～ 126.255.255.255 (127.x.x.x 被保留作本機測試)
	- 預設遮罩： 255.0.0.0(簡寫為 /8)
	- 架構特色： 全球只有 126 個 Class A 網路，但每個網路內部可以容納 224-2 = 16,777,214 台主機

- Class B：中型網路(大型企業、頂尖大學、政府機關)
	- 二進位特徵： 必須以 10 開頭(格式為 10xxxxxx)
	- 十進位範圍： 128.0.0.0 ～ 191.255.255.255
	- 預設遮罩： 255.255.0.0(簡寫為 /16)
	- 架構特色： 全球有 16,384 個 Class B 網路，每個網路可容納 216-2 = 65,534 台主機

- Class C：小型網路(中小企業、學校實驗室、家用網路)
	- 二進位特徵： 必須以 110 開頭(格式為 110xxxxx)
	- 十進位範圍： 192.0.0.0 ～ 223.255.255.255
	- 預設遮罩： 255.255.255.0(簡寫為 /24)
	- 架構特色： 全球有大約 200 萬個 Class C 網路，每個網路只能容納 28-2 = 254 台主機

- Class D：多播(Multicast)
	- 二進位特徵： 必須以 1110 開頭
	- 十進位範圍： 224.0.0.0 ～ 239.255.255.255
	- 架構特色： 不分網路與主機號它不是分配給單一設備的，而是用來做**群組廣播**(例如 IPTV 串流、網路路由協定交換資料)，讓一組設備同時接收同一份資料

- Class E：保留與實驗
	- 二進位特徵： 必須以 1111 開頭
	- 十進位範圍： 240.0.0.0 ～ 255.255.255.255(其中 255.255.255.255 是限制廣播位址)
	- 架構特色： 保留給 IETF(網際網路工程任務組)進行科學研究、實驗或未來規劃使用，一般設備無法公開設定此類 IP

- 傳統定址法為何被淘汰？
傳統分類法的**一刀切**設計在 1990 年代引發了災難因為它缺乏彈性，假設一家中型企業需要連接 2000 台設備：
	- 申請 Class C(上限 254 台)➔ 根本不夠用
	- 申請 Class B(上限 65534 台)➔ 夠用，但會浪費掉 63,000 多個 IP

由於這種死板的分配方式，導致 IPv4 位址在網際網路爆發式成長時迅速枯竭，因此，在 1993 年，這套傳統分類法被 CIDR(無類別域間路由) 徹底取代，改由可任意變更長度的子網路遮罩(如 /21、/22)來進行精準的網路切割

CIDR(無類別域間路由，Classless Inter-Domain Routing) 的表示法是現代網路最核心的 IP 標記方式它徹底打破了傳統 Class A, B, C 的死板邊界，改用最經典的 **斜線表示法**(Slash Notation) 來靈活定義網路的大小
其標準格式為：IP 位址 / 網路位址位元數(例如：192.168.1.0/24)

## CIDR 的運作原理

IPv4 位址總共有 32 個位元(Bits)斜線後面的數字(稱為 Prefix 長度)，代表從最左邊數過來，有幾個位元是屬於**網路號(Network ID)**剩下的位元，自然就歸屬於**主機號(Host ID)**，以 192.168.1.0/24 為例：
- /24 代表前 24 個位元 是網路號(也就是前 3 個字節 192.168.1 鎖定不動)
- 剩下的 8 個位元(32 - 24 = 8)留給主機自由分配
- 轉換成傳統的子網路遮罩，就是 24 個二進位的 1(11111111.11111111.11111111.00000000)，即 255.255.255.0

- 常見 CIDR 表示法與子網路遮罩對照表

利用 CIDR，網路工程師可以任意切出各種奇數長度的網路，以下是業界最常用的 CIDR 標記法對照：

| CIDR | Network address(1 的數量) | Netmask | 可用主機 IP 數量 | 備註 |
| :--- | :---: | :--- | :--- | :--- |
| **`/32`** | 32 | `255.255.255.255` | **1** (2<sup>0</sup>) | 指向**單一特定主機**(常在防火牆或路由表看到) |
| **`/30`** | 30 | `255.255.255.252` | **2** (2<sup>2</sup> - 2) | 用於路由器與路由器之間的**點對點連線(P2P)** |
| **`/29`** | 29 | `255.255.255.248` | **6** (2<sup>3</sup> - 2) | 小型工作室、申請固定 IP 專線的常見規模 |
| **`/26`** | 26 | `255.255.255.192` | **62** (2<sup>6</sup> - 2) | 中小型部門分割(將一個 Class C 再切成 4 塊) |
| **`/24`** | 24 | `255.255.255.0` | **254** (2<sup>8</sup> - 2) | 最常見的區域網路大小(同傳統 **Class C**) |
| **`/22`** | 22 | `255.255.252.0` | **1,022** (2<sup>10</sup> - 2) | 大型企業辦公室、Wi-Fi 設備較多的環境 |
| **`/16`** | 16 | `255.255.0.0` | **65,534** (2<sup>16</sup> - 2) | 大型企業內部總網、雲端 VPC 預設規格(同 **Class B**) |
| **`/8`** | 8 | `255.0.0.0` | **16,777,214** (2<sup>24</sup> - 2) | 跨國電信商、國家級骨幹網路(同 **Class A**) |

- 如何計算可容納的主機數?

	當你看到一個 CIDR 表示法時，可以用一個萬用公式快速算出這個網段可以接多少台設備：

	可用主機數=2<sup>(32-斜線後的數字)</sup>-2

	- 範例一：10.0.0.0/22
		- 主機位元數 = 32 - 22 = 10 位元
		- 總 IP 數 = 2<sup>10</sup> = 1024 個
		- **可用主機數 = 1024 - 2 = 1022 台**

	- 範例二：192.168.1.128/26
		- 主機位元數 = 32 - 26 = 6 位元
		- 總 IP 數 = 2<sup>6</sup> = 64 個
		- **可用主機數 = 64 - 2 = 62 台**

- 為什麼一定要**減 2**

不論網段多大或多小，都必須扣除兩個具備特殊功能的 IP，它們無法指派給一般的電腦或手機：

1. 網路位址(Network Address)： 主機位元全部為 0 的 IP例如 192.168.1.0，代表這個網路的**名稱**，用來寫在路由器的地圖(路由表)上
2. 廣播位址(Broadcast Address)： 主機位元全部為 1 的 IP例如 192.168.1.255，只要把封包寄到這個 IP，同網段內的所有設備都會同時收到

### Private IP
私有 IP 位址（Private IP Address），也就是我們俗稱的**內網 IP**或**虛擬 IP**
在傳統 IPv4 定址分類法（Class A, B, C）的架構下，為了防止網際網路的 IP 太快用完，網際網路工程任務組（IETF）在 [RFC 1918](https://www.rfc-editor.org/info/rfc1918/) 技術文件中，特別從 Class A、B、C 裡面各保留了一段特定的範圍，規定這些 IP 只能在企業內部、學校或家裡等區域網路（LAN）裡自由使用，絕對不能暴露在公開的網際網路上（Internet）

| Classful   | 私有 IP 保留範圍 |  CIDR 表示法 | 私有網路大小 | 適用場景 |
| :--- | :--- | :--- | :--- | :--- |
| **Class A** | 10.0.0.0 - 10.255.255.255 | **10.0.0.0/8** | 1 個大網路 (約 1,677 萬個 IP) | 大型企業內部、跨國集團、AWS 等雲端資料中心 (VPC) |
| **Class B** | 172.16.0.0 - 172.31.255.255 | **172.16.0.0/12** | 16 個連續的 Class B 網段 | 中大型企業、學校電算中心、Docker 容器預設虛擬網路 |
| **Class C** | 192.168.0.0 - 192.168.255.255 | **192.168.0.0/16** | 256 個連續的 Class C 網段 | **最常見！** 家用 Wi-Fi 路由器、中小企業辦公室（如 192.168.1.1） |

### Loopback Address
在 IPv4 的原始分類中，整個 127.0.0.0/8 網段（從 127.0.0.1 到 127.255.255.254）都被劃歸為環迴測試保留區，因此它獨立於 Class A 的一般發放範圍之外，也不屬於 [RFC 1918](https://www.rfc-editor.org/info/rfc1918/) 所定義的那三段私有 IP

### ping localhost 運作流程
當你執行 ping localhost 指令時，它是網管與工程師最常用來檢測**本機網路功能是否正常**的方法，
這個指令的本質是發送 ICMP Echo Request(回應請求) 封包有趣的是，由於 localhost 指向的是本機的環迴介面(Loopback Interface)，資料完全不會流向實體網路線、Wi-Fi 或外部路由器，整個流程都在作業系統的核心核心(Kernel)內部完成。
以下是 ping localhost 從輸入到接收的完整中文網路流程說明：

🌐 第一階段：名稱解析(Domain Name Resolution)

1. 使用者輸入指令：
你在終端機(Terminal / CMD)輸入 ping localhost 並按下 Enter
2. 查詢本地 Hosts 檔案：
作業系統(OS)看到 localhost 這個名字，會優先查閱本地的靜態名稱解析檔案(Windows 為 hosts 檔案，Linux/Mac 為 /etc/hosts)
3. 解析為環迴 IP 位址：
作業系統在檔案中找到對應關係，將 localhost 轉換為本機內部專用的環迴 IP 位址：
	- IPv4： 127.0.0.1
	- IPv6： ::1(現代作業系統通常預設會優先使用 IPv6)

📦 第二階段：傳送端封裝(Encapsulation)

此時，ping 程式開始建立網路封包，並在核心內由上至下進行封裝：
1. 應用程式層(Ping 程式)：
產生一個 ICMP Echo Request 的原始資料
2. L4 傳輸層：
(注意：ICMP 協定直接承載於網路層之上，不使用 TCP 或 UDP，因此不包含 Port 號碼，此步驟會跳過傳輸層的 Port 封裝)
3. L3 網路層(IP 層)：
加上 IP 標頭(IP Header)
	- 來源 IP (Source IP)： 127.0.0.1(或 ::1)
	- 目的 IP (Destination IP)： 127.0.0.1(或 ::1)
4. 路由決策(Routing Decision)：
作業系統的核心檢查目的 IP路由表(Routing Table)發現目標是 127.0.0.0/8 網段，判定這是一個本機內部封包
5. 核心內部攔截(捷徑)：
核心直接將這個封包導向虛擬的環迴網路驅動程式(Loopback Driver)封裝流程在這裡直接中止，封包不會被傳送到 L2 資料連結層(不需查詢 MAC 位址)，也不會到達 L1 實體層(網路卡、網路線)

🔓 第三階段：接收端解封裝(De-encapsulation)

環迴驅動程式在記憶體中直接把剛才傳出的封包**調頭**，轉交給接收端的網路堆疊處理，開始由下至上解封裝：
1. L3 網路層接收：
作業系統的網路堆疊收到這個封包，拆除 IP 標頭，發現目的 IP 是自己，且內部協定是 ICMP
2. 處理 ICMP 請求：
網路核心解析 ICMP 標頭，識別出這是一個 Echo Request (Type 8)
3. 產生回應：
核心的網路模組會自動在記憶體中建立一個對應的 ICMP Echo Reply(回應答覆) 封包

🔄 第四階段：回傳與顯示結果

1. 回傳封裝：
這個新的 ICMP Echo Reply 封包同樣透過環迴介面，在核心內部再次**調頭**傳回給原始的 ping 程式
2. 計算與顯示：
ping 程式收到回應，計算從發出到接收的時間差(通常 < 1ms，因為全在記憶體與 CPU 之間跑)，並在螢幕上印出：
Reply from 127.0.0.1: bytes=32 time<1ms TTL=128

📝 總結：為什麼要 ping localhost？

這個指令的核心價值在於自我檢測
因為它只走完作業系統內部的**網路軟體堆疊(Network Stack)**，完全不經過網卡與外部線路
- 如果 ping localhost 成功：代表你電腦的作業系統網路核心、TCP/IP 協定驅動程式運作完全正常
- 如果 ping localhost 失敗：代表你的作業系統網路功能毀損，或是本機防火牆阻擋了環迴訊號，此時就算換網路線或換 Wi-Fi 也不可能連上網
